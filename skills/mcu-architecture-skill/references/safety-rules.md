# 防御式编程（Fail-Closed）与安全红线

在嵌入式固件开发中，很多偶发死机、硬件失效导致的整机假死，本质上都是因为代码缺乏“防御式设计”。本规范定义了三条必须遵守的架构安全红线。

---

## 红线一：硬件循环等待必须带有超时退出机制

### 1. 痛点：硬件死等导致死机
```c
/* 致命写法：一旦通信总线短路、晶振不起振或从机掉电，MCU 永久死在此处 */
while (I2C_GetFlagStatus(I2C1, I2C_FLAG_BUSY));
while (!SPI_I2S_GetFlagStatus(SPI1, SPI_I2S_FLAG_TXE));
```

### 2. 标准解法：超时边界与错误传播
任何轮询硬件状态位、等待外部响应的循环，必须计算时限并返回错误码：

```c
int Spi_WaitTxEmpty(SPI_TypeDef *spi, uint32_t timeout_ticks)
{
    while (!(spi->SR & SPI_SR_TXE))
    {
        if (timeout_ticks-- == 0)
        {
            return -1; /* 超时失败，将错误向上抛出，不可静默吞掉 */
        }
    }
    return 0; /* 成功 */
}
```

上层调用者接收到 `-1` 时，可以进行：
- 错误重试（如最多重试 3 次）；
- 硬件复位恢复（如重新初始化 I2C 总线并复位外设）；
- 故障报警与安全降级。

## 红线二：中断服务函数（ISR）极度克制

### 1. ISR 中绝对禁止出现的行为
- ❌ 调用 `delay_ms()` 或任何形式的毫秒级阻塞延时；
- ❌ 死等锁或标志位；
- ❌ 复杂的协议解包或数学运算；
- ❌ 调用不可重入的 C 库函数（如 `printf`、`malloc`、`strtok`）；
- ❌ 耗时的 Flash 擦写或长帧串口发送。

### 2. ISR 的标准写法
ISR 的唯一职责是**“抢救现场、搬运数据、发出通知”**：
1. 清除硬件中断触发标志；
2. 将接收到的字节压入环形缓冲区（RingBuffer），或置位触发标志；
3. 退出中断，让主循环去处理。

## 红线三：禁用隐式动态内存分配

### 1. 为什么禁用 `malloc` / `free`？
1. **内存碎片（Heap Fragmentation）**：MCU 的 RAM 通常只有几 KB 到几十 KB。长期运行后，碎片化会导致哪怕总剩余内存充足，也无法申请出一块连续的缓冲区。
2. **内存泄漏与野指针**：裸机系统没有虚拟内存保护，指针越界或泄漏会直接引发硬件 HardFault。
3. **分配耗时不确定**：`malloc` 寻找可用空闲块的时间随碎片程度不可预知，破坏实时性。

### 2. 标准替代方案
- **静态全局/模块静态分配**：驱动控制块、通信缓冲区统一使用全局/静态数组。
- **静态对象池（Object Pool）**：如果需要分配变长消息，预先在 BSS 段分配固定大小的块池，通过位图或静态链表管理借出与归还。
