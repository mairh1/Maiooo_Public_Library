# 通用驱动框架约束

把「跨平台可移植驱动」的架构要求与单片机 C 代码规范落地为可执行动作：**新建驱动**时按框架生成文件骨架并按规范书写，**移植驱动**时守住改动边界，**评审驱动**时按约束逐条检查。约束与芯片、总线、工具链无关。

本 skill 覆盖两层要求：**架构分层与移植契约**（C1–C10）与**代码规范**（S1–S4：命名 / 格式 / 中文 Doxygen 注释 / ISR 与共享数据），两套约束一并执行。

## 设计目标

驱动移植难的根源是硬件访问代码与协议逻辑搅在一起。本框架强制把两者分离：

- **协议 / 算法 / 状态机**沉淀在核心层——纯 C99、零平台代码，任何芯片直接编译
- **所有碰硬件的动作**收敛到一份显式移植契约（`_io.h`）——移植 = 实现契约 + 按需裁剪配置，核心文件零改动

## 四层架构（C1）

```
应用层（用户代码）
    │  drv_xxx.h 公共 API + 统一结果码
┌──────────────────────────────────┐
│ 驱动核心层                          │ 纯 C99，零平台代码
│   drv_xxx.c      协议/算法/状态机   │
│   drv_xxx_conf.h 功能裁剪与配置     │
│   drv_xxx_regs.h 寄存器/协议常量    │
└──────────────────────────────────┘
    │  drv_xxx_io.h 移植契约（固定原型 + 返回码 + 时序/上下文要求）
┌──────────────────────────────────┐
│ 移植层（按平台实现，唯一碰硬件的一层）│
│   port/drv_xxx_io.c               │
└──────────────────────────────────┘
    │
硬件（总线 / GPIO / 片上外设寄存器）
```

仓库内标准范例：`driver/SGM41513_Driver/`（五件套 + port 模板 + README 分层图）、`driver/USB_PD_Driver/`（复杂协议栈的事件回调模式）。设计原理详见[架构设计详解](references/architecture.md)。

## 十条硬约束

### C1 四层架构

驱动固定为五件套文件，核心层零硬件访问：

| 文件 | 职责 |
|---|---|
| `drv_xxx.h` | 公共 API：类型 + 结果码 + 全部函数声明 |
| `drv_xxx.c` | 核心：协议/算法/状态机，不出现任何平台符号 |
| `drv_xxx_conf.h` | 全部配置宏（功能裁剪、变体、调试选项） |
| `drv_xxx_regs.h` | 寄存器/协议常量（片上外设驱动可并入 .h 或省略） |
| `drv_xxx_io.h` | 移植契约：io 函数声明 + 每函数契约注释 |

❌ 核心 .c 里直接调 `HAL_I2C_Mem_Read` / 厂商寄存器操作宏
✅ 核心只调 `drv_xxx_io_read_reg()` 等契约函数

检查：Grep 核心 .c 中的厂商库符号与平台头文件名。

### C2 单向包含

核心 `.c` 的 include 白名单：自身 4 个头 + `<stdint.h>` `<stdbool.h>` `<stddef.h>` `<string.h>`。

- 禁止：厂商库、`app/`、`bsp/`、RTOS / 操作系统头
- `_io.h` 只被核心 include；移植层实现只 include `_io.h` + 平台头
- 依赖只允许自上而下，下层不得感知上层（`_io.h` 不 include 核心 `.h`，上下文用 `void *io_ctx` 透传）

检查：Grep `#include` 逐条对照白名单。

### C3 最小完备移植契约

- io 函数总数 ≤ 7 个；必选函数压到最少（init / read / write / delay 级别）
- 每个函数的 Doxygen 必须回答三问：**返回什么**（返回码语义）、**时序怎么保证**（如延时不允许小于请求值）、**什么上下文能调**（线程 / ISR）
- 按 conf 宏标注 Required / Optional——关闭某功能后，对应移植函数**不再被要求实现**
- io 层返回码统一：`DRV_IO_OK = 0` / `DRV_IO_ERROR = -1`，不透传平台错误码

❌ 移植契约要求实现 15 个回调，其中 10 个只在高级功能里用到
✅ 默认 4 个函数即可跑起来，高级功能按 conf 按需追加

检查：数 `_io.h` 中的函数声明；逐个核对契约注释完整性。

### C4 单头文件裁剪

全部配置宏集中在 `_conf.h`，一律 `#ifndef 默认值` + `#endif`，可在编译器命令行 `-D` 覆盖。

- 裁剪联动：置 0 一个功能开关，对应公共 API 声明、核心实现、io 契约函数**一起**用 `#if` 消失
- 被裁剪 API 的调用在编译期报错（推荐），或保留声明返回 `ERR_NOT_SUPPORTED`——二选一并写进 README
- 禁止把配置散落在核心 `.c` 里，禁止要求用户改库源码来配置

检查：Grep `_conf.h` 中无默认值的裸 `#define`；Grep 核心 `.c` 中 `#if` 与 conf 宏的联动关系。

### C5 平台无关

- 纯 C99：只用 `<stdint.h>/<stdbool.h>/<stddef.h>` 固定宽度类型
- 禁止 `malloc/free`、VLA、递归、编译器扩展、内联汇编
- 硬件等待循环必须带超时退出
- 浮点仅在芯片功能必需时使用（如传感器换算），能定点则定点

检查：Grep `malloc|alloca|asm\s|__attribute|#pragma`。

### C6 统一结果码

`drv_xxx_result_t` 枚举贯穿**全部**公共 API，标准语义集：

| 结果码 | 语义 |
|---|---|
| `OK` | 成功 |
| `ERR_IO` | 通信失败（io 层返回 ERROR 时上抛） |
| `ERR_PARAM` | 参数非法（空指针、超范围） |
| `ERR_NOT_READY` | 未初始化 / 器件无应答 |
| `ERR_NOT_SUPPORTED` | 功能被 conf 裁剪或器件不支持 |

可按需扩展（`ERR_VERIFY`、`ERR_TIMEOUT`），但禁止 `int`/`bool` 与枚举混搭返回状态。

检查：Grep 公共函数声明中返回类型非 `drv_xxx_result_t` 的项。

### C7 多实例句柄

- 设备句柄 `drv_xxx_dev_t` 携带：`io_ctx`（总线句柄透传）+ 设备标识（地址/片选/外设号）+ 运行状态
- 实例由**调用者**定义分配（全局、结构体成员均可）；`init(dev, io_ctx, ...)` 模式
- 核心层允许 `static const` 常量表，禁止可变 `static` 状态（隐藏单例）

❌ `static drv_xxx_dev_t s_dev;` 写死在核心里，第二片芯片没法接
✅ 用户代码里 `static drv_xxx_dev_t dev1, dev2;` 各自 init

检查：Grep 核心 `.c` 中 `^static` 的非 const 变量定义。

### C8 显式线程安全模型

- README 必须写明默认线程安全性（通常：不同实例并发安全，同一实例需外部保护）
- 可选 `DRV_THREAD_SAFE` conf 宏 → 要求移植层实现 `drv_xxx_io_lock/unlock()`，核心在读-改-写临界区前后调用
- 核心不自带锁实现、不直接调用 RTOS API

检查：README 有无线程安全说明；`THREAD_SAFE=1` 时 `_io.h` 是否出现 lock/unlock 契约。

### C9 ISR 约束与事件回调

- 中断服务程序只置标志 / 计数（`volatile`），不做数据处理
- 异步事件经注册回调（`drv_xxx_set_event_cb(dev, cb)`）或事件标志查询上抛，回调在用户上下文执行
- 核心不在 ISR 上下文调用延时/阻塞类契约函数；`_io.h` 中 ISR 安全的函数要注明

检查：Grep 核心中的阻塞等待与回调注册接口。

### C10 文档四件套

每个驱动目录必须包含：

1. `README.md`：分层架构图 + 移植三步走 + conf 配置表 + API 参考表 + 已知坑（来自数据手册的注意事项）
2. `port/drv_xxx_io_template.c`：移植模板，含填空注释与平台示例
3. `examples/<平台>/`：至少一个平台的完整移植示例
4. 结果码语义与物理单位约定（电流 mA、电压 mV 等）写进 API 参考

检查：目录清单对照。

## 代码规范约束（S1–S4）

架构约束之外，驱动代码本身遵循以下规范；❌/✅ 对照示例与修复红线见[代码规范详解](references/code-style.md)。

### S1 命名

| 对象 | 规则 | 正例 |
|---|---|---|
| 文件名 | 全小写 + 下划线，私有头加 `_` 前缀 | `led.c`、`_led_priv.h` |
| 公有函数 | `Module_Function`（模块前缀大写下划线） | `LED_Init()` |
| 文件内静态函数 | 小写 snake_case + 模块前缀 | `ws2812_gpio_init()` |
| 全局变量 | `g_` 前缀 | `g_adc_buffer` |
| 文件级静态变量 | `s_` 前缀 | `s_led_manager` |
| 宏 / 枚举值 | 全大写 | `LED_HW_COUNT` |
| 类型（typedef） | 小写 snake_case + `_t` 后缀 | `led_state_t` |

**驱动目录命名（仅芯片驱动适用）**：一颗外挂芯片对应一个驱动目录时，目录命名为 `<芯片型号>_Driver`，型号大小写与厂商数据手册 / 丝印一致，如 `SGM41513_Driver`、`BQ25622e_Driver`；该规则仅约束芯片驱动——协议栈类组件（如按协议命名的 `USB_PD_Driver/`）及 middleware、skills 等其它目录不受此限，可用全小写 snake_case 或「协议名 + `_Driver` 后缀」。

检查方法：Grep 批量扫（函数定义、`^static`、全局定义等模式），不必逐文件通读。

### S2 格式

- 4 空格缩进，禁止 Tab；单行不超过 100 列；LF 行尾
- **Allman 大括号（BSD 风格）**：`{` 与 `}` 各自单独成行、与控制语句同缩进，`else` 也独立成行；**返回类型独立成行**（BSD KNF）；整个文件必须统一，不允许函数间混用
- 注释一律 `/* */`，不使用 `//`
- 头文件保护：`#ifndef XXX_H` → `#define XXX_H` → 内容 → `#endif /* XXX_H */`，并包 `extern "C"`
- 用 `═══` 分节注释（私有数据 / 类型定义 / API 等分节）组织文件结构

### S3 注释（中文 Doxygen）

- 文件头：`@file @brief @details @note @author @version @date`
- 函数：`@brief @details @param @retval`（每个参数一行对齐）
- 宏、结构体成员、枚举值：尾部 `/**< 说明 */`
- 注释写「为什么」和约束，不复述代码字面

### S4 ISR 与共享数据

- ISR 与主循环共享的变量加 `volatile`；多字节共享数据进临界区
- 重命名公共 API 时强制顺序：Grep 旧名列出全部引用点 → 逐处同步修改 → 再 Grep 旧名确认**零残留**；波及 ≥2 个模块时先列影响面征询用户

## 工作流一：新建驱动

1. **读数据手册 / 参考手册**，提取：总线协议与时序、寄存器表（或外设寄存器组）、功能清单、已知坑
2. **生成骨架**：复制 [assets/drv_conf_template.h](assets/drv_conf_template.h) 与 [assets/drv_io_template.h](assets/drv_io_template.h)，把 `drv_xxx` 前缀替换为实际模块名，按手册填 regs.h
3. **实现核心**：结果码枚举 → 句柄 → init → 按功能分组的 API；set 类函数就近取整到硬件档位并钳位，对应 get 返回实际生效值；全部代码按 S1–S3 书写
4. **写移植模板与文档**：port 模板、README 四件套
5. **自检**：C1–C10 逐条过一遍

## 工作流二：移植到新平台

1. 列出核心五件套，确认本次**只允许**新建/修改 io 实现文件与 conf 覆盖
2. 复制 `port/drv_xxx_io_template.c`，按契约注释填平台实现
3. 按需 `-D` 覆盖或修改 conf
4. **验证核心零改动**：`git diff` 核心 `.c/.h` 必须为空
5. 若发现核心层存在平台依赖——这是驱动自身缺陷，先报告用户，再决定是否按工作流一重构

## 工作流三：评审现有驱动

1. 定位驱动目录，检查五件套是否齐全（C10）
2. 逐条 C1–C10 与 S1–S4 检查（用每条给出的检查方法）
3. 输出违规表：

| 文件:行号 | 约束 | 问题 | 处理建议 |
|---|---|---|---|
| driver/foo/foo.c:12 | C2 | include 了厂商 HAL 头 | 移到 port 层，核心改调 io 契约 |

修复遵循最小改动：能通过补 port 层解决的不动核心；需要动核心结构的先列影响面征询用户。
