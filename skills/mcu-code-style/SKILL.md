# 单片机 C 代码规范检查与自动修复

把单片机嵌入式 C 编码规范落地为可执行动作：按规则清单检查目标代码并**直接修复**，按需生成 `.clang-format` / `.editorconfig`。规则与具体芯片无关，适用于任何 MCU 项目的自有代码层。

## 第一步：解析目标范围

先确定用户要检查什么，范围不明时再问：

- **单文件**：如 `driver/led/led.c`——读该文件及其头文件
- **模块目录**：如 `driver/ws2812/`——Glob 收集目录下所有 `.c`/`.h`
- **全仓库**：Glob 项目自有层的所有 `.c`/`.h`，先统计数量告知用户再动手
- **新写的代码**：以 git diff 或最近改动确定范围

同时定位项目根（含 `.git`、`.cproject` 等标志），后续所有相对路径以项目根为基准。

## 第二步：套用保护清单（只读，绝对不写）

以下内容属于厂商或第三方，**任何情况都不修改**：

| 类型 | 典型目录 / 文件 |
|------|-----------------|
| 官方外设库 / SDK | `Peripheral/`、`SDK/`、`Drivers/`（HAL）、CMSIS |
| 内核支持 | `Core/` |
| 启动文件 | `Startup/` |
| 链接脚本 | `Ld/` |
| 官方系统文件 | `system_*.c/h`、`*_conf.h`、中断文件 `*_it.c` |
| 调试支持 | `Debug/` |
| IDE 工程文件 | `.cproject` `.project` `.template` `.launch` `.wvproj` |
| 构建输出 | `Obj/` `Build/` `release/` |
| 第三方库 | FastLED、u8g2 等（看 LICENSE / README 判定） |

项目自有代码层（可修改）：`app/`、`bsp/`、`driver/`、`middleware/`、`config/` 及入口 `main.c`。目录名各项目不同，按"厂商库之外的业务代码"判断；拿不准时先读文件头注释与 git log，仍拿不准就问用户。

## 第三步：逐规则检查并修复

详细的 ❌/✅ 代码对照示例见[规则对照示例](references/rule-examples.md)——开始逐规则检查前先读它。S1–S5 的规范、优先级与例外以本文件为唯一准则；参考文件仅用于示例，不新增或覆盖规则。

### S1 命名

| 对象 | 规则 | 正例 |
|------|------|------|
| 文件名 | 全小写 + 下划线，私有头加 `_` 前缀 | `led.c`、`_led_priv.h` |
| 公有函数 | `Module_Function`（模块前缀大写下划线） | `LED_Init()` |
| 文件内静态函数 | 小写 snake_case + 模块前缀 | `ws2812_gpio_init()` |
| 全局变量 | `g_` 前缀 | `g_adc_buffer` |
| 文件级静态变量 | `s_` 前缀 | `s_led_manager` |
| 宏 / 枚举值 | 全大写 | `LED_HW_COUNT` |
| 类型（typedef） | 小写 snake_case + `_t` 后缀 | `led_state_t` |

**驱动命名例外（重要）**：芯片 / 片上外设驱动的公共 API 与 io 契约函数一律用「模块前缀小写 snake_case」——如 `ina219_init()`、`ina219_io_read_reg()`，模块前缀为芯片型号小写；`Module_Function` 大写形式适用于应用 / 功能模块（`LED_Init()` 这类）。`_` 前缀私有头仅用于只被核心 `.c` include 的模块内部头（`_led_priv.h`）；五件套中的 `conf / regs / io` 头面向用户与移植者，不加 `_` 前缀。

**驱动目录命名（仅芯片驱动适用）**：一颗外挂芯片对应一个驱动目录时，目录命名为 `<芯片型号>_Driver`，型号大小写与厂商数据手册 / 丝印一致，如 `SGM41513_Driver`、`BQ25622e_Driver`；该规则仅约束芯片驱动——协议栈类组件（如按协议命名的 `usb_pd_driver/`）及 middleware、skills 等其它目录不受此限，可用全小写 snake_case 或「协议名 + `_Driver` 后缀」。

检查方法：Grep 批量扫（函数定义、`^static`、全局定义等模式），不必逐文件通读。

### S2 格式

- 4 空格缩进，禁止 Tab；单行不超过 100 列；LF 行尾
- **Allman 大括号（BSD 风格）**：`{` 与 `}` 各自单独成行、与控制语句同缩进，`else` 也独立成行；**返回类型独立成行**（BSD KNF）；整个文件必须统一，不允许函数间混用
- 注释一律 `/* */`，不使用 `//`
- 头文件保护：`#ifndef XXX_H` → `#define XXX_H` → 内容 → `#endif /* XXX_H */`，并包 `extern "C"`
- 用 `═══` 分节注释（私有数据 / 类型定义 / API 等分节）组织文件结构

### S3 注释（中文 Doxygen）

- **注释优先使用中文**：说明性注释一律优先用中文书写，不写整段英文注释；没有通用中文译法、不好翻译的单词保留英文或原文（如 burst、fuel gauge、USB PD 的 Source/Sink、JEITA），推荐「中文(原文)」夹注写法，禁止强行硬译；Doxygen 关键字（`@brief` 等）、专有名词、寄存器名保持英文原词；标识符命名仍按 S1 用英文——命名英文、注释中文搭配
- 文件头：`@file @brief @details @note @author @version @date`，标准写法：

```c
/**
 * @file    led.c
 * @brief   一句话说明模块职责
 * @details 实现要点逐条列出：
 *          - 要点一
 *          - 要点二
 * @note    依赖与约束（如：仅依赖自身头文件与 C99 固定宽度类型头）
 * @author  （作者）
 * @version 1.0.0
 * @date    YYYY-MM-DD
 */
```

- 函数：`@brief @details @param @retval`（每个参数一行对齐），说明文字用中文
- 宏、结构体成员、枚举值：尾部 `/**< 中文说明 */`
- 注释写「为什么」和约束，不复述代码字面

### S4 ISR 与共享数据

- ISR 与主循环共享的变量加 `volatile`；多字节共享数据进临界区
- 重命名公共 API 时强制顺序：Grep 旧名列出全部引用点 → 逐处同步修改 → 再 Grep 旧名确认**零残留**；波及 ≥2 个模块时先列影响面征询用户

### S5 可读性与可维护性

- 所有新增或修改的代码必须便于人类阅读、理解、调试和维护
- **可读性优先于节省 token、字符数或行数**：允许消耗更多 token，把实现写清楚；禁止为了压缩输出而生成晦涩、高度压缩的代码
- 使用含义明确的命名、清晰的控制流程和职责单一的函数；复杂表达式拆成有意义的中间变量和步骤，避免多条语句挤在一行、嵌套三元表达式及隐藏执行逻辑的宏
- 注释解释设计原因、硬件约束、单位和关键计算依据，避免无意义注释和无必要的抽象
- 禁止编写与实际功能、需求或缺陷无关的测试代码、验证脚手架和校验值；不得为展示“已验证”而增加无意义的断言、硬编码期望值或自证逻辑。必要的协议 CRC、校验和、参数检查及有依据的测试数据不属于此禁令

检查：阅读新增或修改的代码，确认控制流程和关键计算可直接理解，命名与注释足以说明意图，测试和校验值有明确的需求或协议依据。

### 通用架构与嵌入式安全检查项

适用于应用 / BSP / 功能模块等自有业务代码；可移植驱动核心另有更严的多实例与契约约束，不在本节展开。

检查项：

- **分层**：`main → app → bsp → driver/middleware → 厂商库`；上层 include 下层，**禁止反向**。驱动、中间件不得 include `app/`、`bsp/` 层头文件
- **模块内部状态**：业务模块内部状态一律 `static` + 访问函数，不裸露全局变量
- **头文件自包含**：include 自己直接用到的依赖
- **平台无关基础**：纯 C99 固定宽度类型；禁止 `malloc/free`、VLA、递归、编译器扩展、内联汇编；硬件等待循环必须带超时退出；浮点仅在芯片功能必需时使用，能定点则定点
- **ISR 约束**：中断服务程序只置标志 / 计数（`volatile`），不做数据处理；禁止在 ISR 内 printf、延时、阻塞等待或大循环；核心逻辑经回调或事件标志在用户上下文执行

检查：Grep include 确认依赖方向；Grep `malloc|alloca|asm\s`；定位 ISR 函数体查 printf/Delay/无超时 while。

## 第四步：执行流程

默认**检查 + 直接修复**（用户明说"只检查不修"时只输出报告）：

1. **收集目标**：按第一步范围 Glob `*.c` `*.h`，排除保护清单目录
2. **逐规则检查**：S1 用 Grep 批量；S2/S3 读文件逐段看；S4 定位共享数据与重命名点；S5 通读新增/修改逻辑可读性；通用项 Grep include 与 ISR/危险分配
3. **直接 Edit 修复**：同一文件内的格式、注释问题一次修完
4. **命名重构强制顺序**（违反会引入编译错误，必须严格执行）：
   Grep 旧名列出全部引用点 → 逐处同步 Edit → 再 Grep 旧名确认**零残留**。
   公共 API 重命名波及 ≥2 个模块时，先列出影响面征询用户，确认后再动手
5. **提醒用户重新编译**验证（本 skill 不执行编译）
6. **输出汇总表格**：

   | 文件:行号 | 规则 | 问题 | 处理 |
   |-----------|------|------|------|
   | driver/led/led.c:89 | S2 | for 循环 K&R 大括号 | 已转 Allman |

## 修复红线（不可越过）

S5 的可读性要求不授权在规范修复中擅自改变执行逻辑，仍须遵守以下红线。

- 不改任何执行逻辑、运算、时序——只动标识符、空白、注释
- 不删用户已有注释，只补充和修正
- 中断向量名、`*_IRQHandler`、启动文件中注册的符号**绝对不改**
- 保护清单内的文件绝对不动
- 厂商 / 第三方内容任何情况都不修改：官方外设库 / SDK（`Peripheral/`、`SDK/`、`Drivers/`、CMSIS）、内核支持 `Core/`、启动文件 `Startup/`、链接脚本 `Ld/`、`system_*.c/h` 与 `*_it.c`、IDE 工程文件（`.cproject` `.project` `.launch` 等）、构建输出目录、第三方库（看 LICENSE / README 判定）
- 保持 LF 行尾，不引入 CRLF / BOM
- 修复涉及行为语义时（如给等待循环加超时会改变返回路径），只标记问题不动手，说明理由留给用户决定

## 配置生成模式

用户要求生成 `.clang-format` / `.editorconfig` 时：

1. 复制 `assets/clang-format` → 项目根 `.clang-format`
2. 复制 `assets/editorconfig` → 项目根 `.editorconfig`

生成后做非破坏性验证：

- 先确认目标项目实际使用的 clang-format 版本，再用该版本对代表性的 `.c` / `.h` 文件执行 dry-run（例如 `clang-format --dry-run --Werror --style=file <file>`），确认资产可解析。
- 检查 `.editorconfig` 语法及项目的行尾约定；配置已复制不等于验证通过。
- 当前环境没有 clang-format 或无法执行 dry-run 时，输出中明确标记“未完成运行时验证”，不得声称资产已验证。

并告知用户：`.clang-format` 只能覆盖 S2 格式类规则；S1 命名、S3 注释、S4 ISR 与共享数据、S5 可读性是任何格式化工具都做不了的——这些正是需要本 skill 的部分。
